## QQ 授权登录（替代 5.2 的用户名密码登录）

**背景**：用户对 5.2 的账号密码登录不满意，要求改成「QQ 授权登录」。
标准 QQ 互联 OAuth 不可行——要求开发者实名 + **已 ICP 备案的回调域名**，本项目跑内网 localhost。
改为「机器人私聊发一次性验证码」，复用已有 NapCat + send_bridge，体验等价且零外部依赖。

**新增/改动（Java）**
- `auth/QqLoginService.java`（新）：只向 `app_setting.owner_sender_id`（兜底 `AUTH_OWNER_QQ`）发 6 位码；
  Redis 键 `auth:qq:code:<qq>`（TTL 5min）/ `auth:qq:cooldown:<qq>`（60s）/ `auth:qq:attempt:<qq>`；
  常量时间比对，连错 5 次作废；发码失败会删掉已写入的码。
- `auth/AuthService.java`：抽出 `createSession(username)` 与 `sessionUsername()`，密码登录与 QQ 登录共用同一会话出口。
- `auth/AuthController.java`：新增 `GET /api/auth/qq/status`、`POST /api/auth/qq/code`、`POST /api/auth/qq/verify`。
- `auth/AuthWebConfig.java`：放行 `/api/auth/qq/**`。
- `application.yaml`：`app.auth.owner-qq` / `qq-code-ttl-minutes` / `qq-code-cooldown-seconds` / `qq-code-max-attempts`。

**关键坑**：发送桥按 `bizRef` 幂等，登录码的 `bizRef` 必须每次唯一
（`auth-login:<qq>:<uuid>`），否则第二次登录会被吞掉、收不到码。

**测试**：新增 `QqLoginServiceTest`（16 例）。另发现 5.2 引入的 `AuthInterceptor` 把 7 个 controller
集成测试全挡成 401（23 个失败，是既有问题）——新增 `support/StubAuthConfig`（`@Primary` 的 mock
AuthService）+ 各测试 `@Import`，全部修复。**没有**在生产代码里加「关鉴权」开关。

**前端**：`LoginView.vue` 改双页签（QQ 登录默认 / 密码登录兜底），6 位输满自动提交；
`api/auth.ts` 加三个方法；设置页「我的 QQ 号」补说明（也是登录收码账号）。

**文档**：`design_overview.md` §5.2 重写（含为什么不用 OAuth）；`api_contract.md` 新增第十五章 +
总览表；`deploy/README.md` 新增 §6.2 与排错行；`.env.example` 加 `AUTH_OWNER_QQ`；README 更新已知限制。

## Bug：总开关关了，文件任务仍自动回复

**现象**：设置里「自动回复 → 总开关」关掉后，对方发 PDF，机器人仍回
「这个格式我只能读不能改，换成 xlsx/docx 吧」。

**根因**：这句话不是 Dify 生成的，是插件 `core/file_task.py:358` 在
`download_and_prepare()` 里直接 `reply_text`，**完全绕过了 `reply_gate`**。
`reply_gate` 只作用于 `_respond()` 里 Dify 返回的信封，而文件消息在 `ingest()`
阶段就把话说完了。同类绕过点还有 182/197/225/298/344 行。

**修法**（不改 file_task，把闸提前到下载之前）：
- Spring：`ReplyContextVO` 加 `ownerSenderId`（取自 `app_setting.owner_sender_id`），
  `ChatSettingServiceImpl.replyContext` 填充。
- 插件：新增 `_fetch_reply_context()` / `_is_owner()`；
  `_handle` 文件分支先取快照，`may_reply = enabled or sender_id == ownerSenderId`，
  不满足就**不下载、不建任务、不调 Dify、不回复**；`_respond` 新增可选 `reply_ctx`
  参数复用同一份快照（不重复打接口）。
- 语义：关掉开关 + 别人发文件 → 闭嘴；关掉开关 + **主人自己**发文件 → 照常（用工具≠替主人说话）。
  拿不到主人号按「不是主人」处理（fail closed）。

**兼容性**：只更新插件不更新 Spring → `ownerSenderId` 缺失 → 一律按非主人，行为正确但主人自己的
文件任务在关开关时也会被忽略；两边都更新才是完整行为。

**测试**：插件 +2 例（他人文件被忽略 / 主人文件仍处理且只取一次快照），插件全量 148 绿；
Java `ReplyContextTest` +2 例（14 绿）。前端设置页文案同步改（原来说「文件填写不受影响」是错的）。

## 需求变更：总开关 = 彻底一个字都不说

**用户原话**：「关了就是彻底一个字都不说」。即 `TASK`（备忘确认语）、拦截规则回复、
文件任务应答也一并停。

**关键设计点**：原来的 `enabled` 是「总开关 AND 会话开关 AND 令牌桶」三层相乘，
插件分不出是哪层关的。直接拿它停 TASK 会导致「某个群关了自动回复 → 该群的备忘确认语也没了」。
所以 `reply-context` 新增 `globalEnabled`（只反映 `app_setting.reply_enabled`）：

| 字段 | 关掉后 |
|---|---|
| `globalEnabled` | 彻底闭嘴：CHAT + TASK + 拦截回复 + 文件任务应答全停 |
| `enabled` | 只停 CHAT（会话开关关掉时 TASK 仍发） |

**实现两层兜底**：
1. `reply_gate.decide`：`globalEnabled=false` → 静默（`suppressed="mute"`），只清 content，
   action 照跑（备忘照建）。
2. `core/reply.py` 新增 `silence()`（ContextVar）+ `reply_text` 首行检查。
   `_respond` 拆成薄包装 + `_respond_inner`：总开关关时整轮跑在 `silence()` 里。
   **原因**：直接回话的点散在 `file_task`（过期提示/格式不支持/FILE_FILL 结果）、
   `dispatch`、拦截分支里七八处，逐个判断必然漏。`FILE_FILL → apply_fill` 就是漏网的一条。
3. `_intercept`：总开关关时整条跳过，且**不 mark**（没发出去不算已回复）。
4. 文件分支：`may_reply = globalEnabled and (enabled or isOwner)`。

**仍会发**：到点备忘提醒（Java 调度器 → send_bridge，不经插件），以及网页草稿中心里
用户手动点确认的发送。UI 文案已写明「提醒仍会私聊发给你，那不是回复别人」。

**兼容**：`globalEnabled` 缺失（旧 Spring）时按 `true` 处理——`normalize` 里单独处理，
不能走 EMPTY_CONTEXT 的布尔默认（`bool(None)` 会变成 False，一升级插件全员失声）。

**测试**：插件 159 绿（+11：gate mute 3 例、normalize 3 例、reply.silence 3 例、
listener 2 例）；Java `ReplyContextTest` 16 绿。前端 build 通过。

## UI：群设置列表行被长群名挤变形

**现象**：群名过长时，右侧「整理」「自动回复」被压成竖排（整/理、自动回/复）。

**根因**：`.chat` 是 flex 行，但 `.chat-switches` 没有 `flex: 0 0 auto`、`.mini` 没有
`white-space: nowrap`、`.chat-name` 缺 `flex: 1 1 auto` + `min-width: 0`
（flex 项默认 `min-width: auto`，少了这行 `text-overflow` 不生效）。浏览器于是优先压缩开关组。

**改法**（`ChatSettingsView.vue`）：
- 名字取第一段：`chatLabel` 用 `/[，,、;；]/` 分割，别名与群名都只留第一段；
- `.chat-name` 单行 + 省略号；`:hover`/`:active` 时改为 `overflow-x: auto` 可横向滑动看全，
  滚动条隐藏；`title` 挂完整群名（桌面悬停）；
- `.chat-switches` 加 `flex: 0 0 auto`，`.mini` 加 `white-space: nowrap`。

**验证**：用 Edge headless 在 390px 容器内渲染实测（`row.client == row.scroll` 无溢出，
`name.client 255 / scroll 354` 省略号生效）。注意 Edge headless 的 `--window-size` 有最小
宽度限制（约 500），截图会骗人，必须用固定宽度容器或量 `getBoundingClientRect`。

## UI：草稿卡片「对方 · 名字」重复且撑破两行

**现象**：回复草稿的引用块显示成
`对方 · 低代码开发课程三班(2025)，低代码开发课程三班(2025)`，把整段引用挤到第三行被裁掉。

## 5.4 NapCat 掉线补拉（已实现）

**边界**：NapCat 掉线期间 QQ 根本没推消息，MQ 变不出来；真正能补的是「重连后回查历史」。
所以不做 Redis Stream，只做重连补拉。

**Spring 侧**
- 新表 `napcat_cursor(chat_type, chat_id, last_message_seq, updated_at)`，
  `uk_napcat_cursor(chat_type, chat_id)`；已用 mysql 客户端在 `qq_assistant` 库建好。
- `NapcatCursorServiceImpl.targets()`：两路合并后按 `(chatType, chatId)` 去重——
  ① 开了自动回复/整理的 `chat_setting`（**排前面**，撞 50 上限时不能被闲聊群挤掉）；
  ② 近 7 天有 `message_log` 的群/私聊，按活跃倒序。私聊 `chatName` 恒为 null。
- `advance()`：`INSERT ... ON DUPLICATE KEY UPDATE last_message_seq = GREATEST(...)`，
  再**回读**返回实际值（回显入参会骗过调用方）。不用「先查再写」，那有并发覆盖窗口。
- `GET /api/agent/napcat/targets` + `POST /api/agent/napcat/cursor`；
  业务拒绝走 HTTP 200 + code=400（与 `/api/agent/ops` 一致）。
- `MessageLogItem` 新增 `createdAtEpochSeconds`：补拉要落回原始时刻。
  用 epoch 不用 ISO 串——插件在容器里，时区未必是 Asia/Shanghai，传墙钟会整体偏 8h。
  `BeanUtils.copyProperties` 遇到类型不可赋值的属性**静默跳过**（不抛异常），换算必须显式做。

**插件侧**
- `core/napcat.py`：`get_status` / `get_group_msg_history` / `get_friend_msg_history`。
  `status=="failed"` 也算失败——OneBot 是 HTTP 200 + 业务失败，只看状态码会把
  「群号不存在」当成「没有历史」，然后静默跳过。`trust_env=False` 防系统代理接走 127.0.0.1。
- `core/backfill.py`：`_was_online=None` 起步，所以「启动即在线」也会补一次；
  按 `message_seq` 向前翻页（`page_seq = 本页最小 seq`），到 `<= 游标` 或页数/条数上限即停；
  **整页 `log_messages` 成功才 `advance_napcat_cursor`**（不走 log_queue，必须拿到确定结果）。
  硬上限 50 会话 / 200 条 / 5 页 × 40 / 1 req/s。
- 补上的两个坑：① 历史里混着**机器人自己的消息**，按 `sender_id == bot_qq` 跳过
  （否则检索会把机器人的话当对方证据）；② 媒体消息给 `[图片]/[文件] 名字` 占位，
  `msgType` 用 `file`/`image`，`MessageNoiseFilter` 只对 `text` 做噪音判断，非 text 一律保留。
- `main.py` 接线 + `terminate` 里 `await backfill.stop()`；配置新增
  `napcat_backfill_enabled/interval_s/start_delay_s`（`_flag` 处理 "false" 字符串，
  不能用 `bool(value)`）。manifest 0.2.27 → **0.2.28**。

**去重键统一**：实时 IN 日志从 `log:<uuid>` 改成 `msg:<message_id>`，
与补拉路径一致，靠 `message_log.uk_dedupe` 吞掉重叠。

### 追问修复：NapCat 重启后补拉不触发

用户报「NapCat 重启 / 退出重登后，中途消息还是不被 LangBot 消费，好像无关插件」。
分层确认：事件推送丢的确实补不回来（插件只能在 LangBot 交事件之后才有机会干活），
但补拉**不走事件推送**，是主动查 NapCat 历史，所以这条路仍然有效。

**真 bug（已修）**：`tick()` 里 `await self._napcat.online()` 抛异常时直接冒到 `_run`，
`self._was_online = bool(online)` 那行没执行 → 一直停在 `True` →
NapCat 回来后 `online and not True` 恒 False → **永远不补拉**。
NapCat 重启/退出登录期间 HTTP 是关的，异常恰恰就是掉线信号。现在 `tick()` 自己
catch，置 `_was_online = False` 并返回 False（`_was_online is not False` 时才打一次 warning）。

**间隔 30s → 10s**：NapCat 重启只要十几秒，30s 一次有 2/3 概率整个窗口没探到。
`get_status` 是本机 HTTP、几乎零成本，10s 把漏检概率降到 ~20%。
`max(5, ...)` 下限保留。

**仍未覆盖的角落**：NapCat 一直在线、只有 LangBot 的 WS 客户端断了 ——
`get_status` 全程 true，补拉不会触发。要么靠 LangBot 自己重连，
要么加低频兜底补拉（代价：持续打历史接口，可能触发 QQ 风控），暂未实现，等用户拍板。
