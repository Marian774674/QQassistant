# Context
我正在开发一个基于多组件协同的QQ消息智能助手。
- **消息接入层**：NapCat (提供QQ协议) + LangBot (消息路由、插件管理、前置拦截)。
- **AI 大脑层**：Dify (负责意图识别、Agent 编排、对话管理、Tool 调用)。
- **业务逻辑层**：Spring Boot (负责状态管理、文件处理、用户画像存储、备忘录业务逻辑)。
- **前端展示层**：Vue3 (备忘录管理、草稿确认、用户画像配置)。

# Core Features & Optimizations (核心功能与优化方案)
请深刻理解以下业务逻辑及我采纳的优化方案，在后续设计和编码中严格遵循这些组件边界：

## 1. 私聊拟人回复
- **逻辑**：模仿用户语气进行人性化回复。
- **优化方案**：
  - **拟人延迟**：在 LangBot 层实现打字延迟机制，根据字数模拟真人阅读和输入时间。
  - **草稿/静默模式**：非紧急或低置信度的回复，Dify 生成后不直接发送，而是通过 API 推送到 Vue 前端作为“草稿”，由用户一键确认发送。

## 2. 统一回复任务（如群收集学号）
- **逻辑**：识别群内收集信息通知，自动读取知识库并回复。
- **优化方案**：
  - **状态防重**：Spring Boot 维护“待办收集任务”状态表。Dify 识别意图后，调用 Spring Boot API 检查是否已回复，防止重复回复。
  - **前置拦截**：高频固定回复（如学号）在 LangBot 层使用正则前置拦截， bypass Dify 以节省 Token 并提高响应速度。

## 3. 备忘录与提醒功能
- **逻辑**：识别邀约、通知等关键信息，存入备忘录并设置提醒。
- **优化方案**：
  - **重要性分级**：Dify 调用备忘录 API 时，必须输出“重要性等级(1-5)”和“分类标签”。
  - **动态提醒**：5级强提醒，3级温和提醒，1级仅静默记录。

## 4. 复杂任务处理（文件相关）
- **逻辑**：处理涉及文件的任务（如填表），自动填入已知信息。
- **优化方案（业务后置）**：
  - **严禁 Dify 直接处理文件流**。
  - **工作流**：QQ 收到文件 -> LangBot 下载至 Spring Boot 本地 -> Dify 识别意图并调用 Spring Boot 暴露的“文件处理 Tool/API” -> Spring Boot 读取文件、从知识库获取信息并填入、生成新文件 -> Spring Boot 将文件上传回 QQ，并同步状态至 Vue 备忘录。

## 5. Agent 持续学习机制（核心难点）
- **逻辑**：学习用户的聊天方式、性格、目标、身份信息。
- **优化方案（记忆分离）**：
  - **事实记忆**（学号、姓名、目标）：高置信度提取，存入 Spring Boot 数据库，作为 Dify 的外部知识库或变量注入。
  - **风格记忆**（语气、性格）：禁止实时修改 System Prompt。采用“定期总结机制”（如每日凌晨触发），分析当日聊天记录，提炼风格特征，更新 Dify 的“用户画像 Prompt”或通过 Few-shot 动态注入历史真实回复。

# Rules & Constraints (规则与约束)
1. **组件边界清晰**：在设计时，严格区分 Dify（擅长语义理解、意图识别、对话流）和 Spring Boot（擅长状态机、文件IO、复杂业务逻辑、持久化）的职责。不要把业务逻辑写进 Dify 的 Prompt 里。
2. **代码规范**：Spring Boot 代码需遵循 RESTful 规范，使用合理的异常处理和统一返回格式；Vue 代码需使用 Composition API (setup 语法糖) 和 TypeScript。
3. **接口设计**：在编写代码前，优先定义好 LangBot/Dify 与 Spring Boot 之间的 API 契约（如 JSON 结构）。
4. **思考过程**：在给出复杂架构或代码前，先简要说明你的设计思路，特别是数据流向和组件交互过程。
