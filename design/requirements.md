## 1. 项目背景与目标

### 1.1 背景

个人日常在 QQ 上要处理三类重复劳动：

1. **聊天回复**：同学群里的收集通知、私聊里的邀约，需要及时、像本人语气地回。
2. **信息留存**：通知里带时间的事项容易漏；散落的个人信息（学号、姓名、专业）每次填表都要重填。
3. **文件填写**：班委发来的 xlsx / docx 表格，本质是把「已知信息填进指定单元格」，重复且枯燥。

### 1.2 产品目标

做一个**跑在自己机器上、以 QQ 为唯一入口**的个人助手：它在 QQ 上收发消息与文件，由大模型判断语义与意图，由工程代码负责状态、持久化与文件读写。

可度量的目标：

| 编号 | 目标 | 度量方式 |
|---|---|---|
| G-1 | 私聊消息能得到符合本人语气的回复，且不刷屏、不像机器人 | 人工体验验收；延迟公式见 FR-2.2 |
| G-2 | 群里的收集类通知不再重复回复 | 同一 `task_key` 只回复一次（FR-3） |
| G-3 | 带时间的邀约/通知能按重要性分级提醒 | 提醒条数与提前量符合策略表（FR-4.3） |
| G-4 | 收到表格后能自动填写并回传，缺信息时在 QQ 里追问 | 端到端验收 UC-05 / UC-06 |
| G-5 | 记住「我本人」的事实信息，跨会话复用；语气画像定期更新 | `profile_fact` 命中率；画像版本可查 |
| G-6 | 凡是 AI 可能判断错的产出，都能降级成草稿由人确认 | 四类草稿均可确认/拒绝（FR-8） |

### 1.3 非目标（明确不做）

- 不做多用户 / 多租户：单实例、单主人，`sender_id` 即本人。
- 不做 QQ 协议逆向或自研协议端：一律走 NapCat。
- 不做移动端 / 桌面端 App，前端只有 Web。
- 不做公网部署与多机水平扩展：内网单机。
- 不把助手做成通用聊天机器人：只服务上述五类场景。

## 2. 用户与场景

### 2.1 用户角色

| 角色 | 说明 | 交互界面 |
|---|---|---|
| **主人（唯一用户）** | 助手的拥有者，所有记忆与草稿属于此人 | QQ（主入口）+ Vue Web（管理与确认） |
| 群成员（间接） | 与机器人在同一群、可能看到它的回复 | QQ 群 |
| 私聊对象（间接） | 与机器人私聊的人，收到的是主人语气的回复 | QQ 私聊 |

### 2.2 用例清单

| 编号 | 用例 | 触发 | 主要输出 | 关联需求 |
|---|---|---|---|---|
| UC-01 | 私聊普通聊天 | 私聊发一条文本 | 拟人延迟后的回复，或草稿，或静默 | FR-1, FR-2 |
| UC-02 | 群内收集通知自动回复 | 群消息命中拦截规则或意图 | 回复一次并标记已回 | FR-1, FR-3 |
| UC-03 | 记录备忘并分级提醒 | 消息含邀约/截止时间 | `memo` + 多条 `memo_reminder`，到期推送 | FR-4 |
| UC-04 | 先说要求再发文件 | 「我要发个文件，把姓名填上」→ 发文件 | 不回问、直接按已述要求填 | FR-5 |
| UC-05 | 先发文件再补要求 | 发文件 → 「姓名张三，学号2023001」 | 追问一次后按补充信息填 | FR-5 |
| UC-06 | 低置信填写转草稿 | 填写置信度不足 | 草稿中心确认后文件才发出 | FR-5, FR-8 |
| UC-07 | 备忘闭环 | 提醒发出后回「做完了」 | 备忘置 DONE | FR-4.5 |
| UC-08 | 记忆纠错 | 记忆总控台增删改事实 | 下一次会话立即生效 | FR-6 |
| UC-09 | 风格画像更新 | 定时任务 / 手动触发 | `style_profile` 更新 | FR-6.3 |
| UC-10 | 人工确认草稿 | 草稿中心点确认 | QQ 真的收到文本或文件 | FR-8 |

## 3. 总体架构与硬性约束

### 3.1 架构

```
QQ ──► NapCat（QQ 协议）──► LangBot + QQ 助手插件（路由 / 拦截 / 拟人延迟 / 文件 I/O）
                                  ├──► Dify Chatflow（意图、对话状态、决策「填什么 / 发不发」）
                                  └──► Spring Boot（状态机、持久化、定时调度、草稿中心）
                                              └──► Vue3（首页 / 备忘 / 草稿 / 问一句 / 记忆与设置）
Spring Boot ──► 发送桥 send_bridge ──► LangBot / NapCat（主动发文本、发文件）
```

### 3.2 组件边界（硬性需求 C-1 ~ C-4，不可违反）

| 编号 | 约束 | 判定方式 |
|---|---|---|
| **C-1** | 业务逻辑不得写进 Dify Prompt。状态机、持久化、定时调度归 Spring Boot；文件 I/O 归 LangBot 插件。Dify 侧只允许出现**语义判断、JSON 决策，以及对 `POST /api/agent/ops` 的调用**；提示词里不得出现提醒策略、状态迁移规则、阈值 | PR 评审：Dify 的提示词/代码节点里搜不到阈值与状态机；业务规则改动只改 Spring 服务层 |
| **C-2** | Dify 不得接触文件流。只接收插件结构化后的文本，只返回 `fills` / `missing` | 插件代码中不存在 Dify 传文件的路径 |
| **C-3** | 风格记忆不得实时修改 System Prompt，只能由定期总结更新；事实记忆可实时写 | 无单条消息触发的 prompt 写接口 |
| **C-4** | Spring Boot 不得直连 NapCat。一切 QQ 动作经 LangBot / 发送桥 | 后端配置里只有 `langbot.base-url` |

### 3.3 组件职责

| 组件 | 负责 | 不负责 |
|---|---|---|
| **NapCat** | QQ 协议、收发消息与文件、HTTP/WS 接口 | 任何业务判断 |
| **LangBot + 插件** | 事件归一化、群聊触发判定、正则前置拦截、拟人延迟、文件下载/解析/回写/回传、动作执行、幂等 | 长期业务状态、定时任务 |
| **Dify** | 意图识别、对话状态（本轮是否在等文件）、语义生成、决策 envelope | 持久化、文件二进制、定时 |
| **Spring Boot** | 12 张表的持久化、提醒调度、草稿确认分发、画像存取 | 文件流、直连 QQ |
| **Vue** | 展示、人工确认、手动编辑与配置 | 业务判定逻辑 |

## 4. 功能需求

编号规则：`FR-<模块>.<序号>`。每条需求若含「降级」段落，指的是异常情况下系统**必须**如何退化——宁可不回复，也不能发错内容。

### FR-1 消息接入与触发

**FR-1.1 私聊**：私聊文本一律进入处理管线。
**FR-1.2 群聊**：仅当消息 **@ 机器人** 或以配置的**触发前缀**（默认 `!`）开头时处理；其他群消息必须忽略，不得送往 Dify。理由：成本与打扰。
**FR-1.3 文件消息**：私聊与群聊（满足 1.2 条件时）的 xlsx / docx / pdf 附件进入文件管线（FR-5）；其他格式按普通消息处理并给出说明。
**FR-1.4 消息去重**：同一条 QQ 消息重复投递时只处理一次（按 `message_id` / `dedupe_key`）。
**FR-1.5 自身消息**：机器人自己发出的消息不得再次触发处理。

**降级**：任一上游（Spring / Dify / NapCat）不可达时，本条消息记日志并结束，进程不得崩溃；文件任务保留可恢复状态。

### FR-2 私聊拟人回复与草稿

**FR-2.1 发送决策由 Dify 作出**：每条待回复消息，Dify 返回 `SEND` / `DRAFT` / `SILENT` 之一（随统一决策 envelope，见 `agent_contract.md`）。插件不得自行用阈值改写决策。
**FR-2.2 拟人延迟**（仅私聊，群聊不启用）：

- 延迟 = `1.5s + 字数 × 0.15s + 随机抖动(0~1.0s)`
- 上限 15s（封顶）
- 四个参数（基础、每字、抖动、上限）必须可配置

**FR-2.3 语气**：回复由 Dify 依据「事实记忆 + 风格画像」生成，读起来应像本人；不得出现「作为AI」「很高兴为您服务」之类的机器人口吻。
**FR-2.4 静默**：`SILENT` 时只记日志，不推不送。
**FR-2.5 草稿**：`DRAFT` 时写入统一草稿中心（`type=REPLY`），不直接发 QQ。

**降级**：Dify 返回的 Answer 不是合法决策 JSON 时，**不得把原文发给用户**，一律降级为 `SILENT` 并记录告警。

### FR-3 统一回复任务（防重 + 前置拦截）

**FR-3.1 前置拦截**：高频固定回复（如报学号）由插件按「关键词 + 正则」在本地拦截，绕过 Dify 以省 token、降延迟。
**FR-3.2 规则热更新**：规则存于 Spring 的 `intercept_rule` 表，插件定时拉取（默认 60s），改规则不需改代码、不需重启。
**FR-3.3 拦截后仍查防重**：命中规则后必须先调 `collection-tasks/check`，确认本 `task_key` 未回复过才发；发完调 `mark`。
**FR-3.4 `task_key` 定义**：`chat_id + task_type + 时间窗口`（当天 / 本周可配）。既防重，又不误拦新批次。
**FR-3.5 未命中**：交给 Dify 识别，走同一条 check / mark 防重路径。

**验收**：同一收集任务在群内被两人同时触发，只产生一条回复。

### FR-4 备忘录与分级提醒

**FR-4.1 识别与抽取**：Dify 从消息中识别邀约/通知，输出 `title`、`content`、`importance(1-5)`、`category`、`dueTime`。
**FR-4.2 分级 rubric**（必须体现在 Dify Prompt 中，含边界与示例）：

| 级别 | 判定标准 | 例子 |
|---|---|---|
| 5 | 有明确时间 + 不做后果严重 | 考试、面试、答辩 |
| 4 | 有明确时间 + 重要但可调整 | 重要邀约、缴费截止 |
| 3 | 普通邀约 / 一般截止 | 班会、聚餐 |
| 2 | 低价值待办 | 帮带东西 |
| 1 | 纯信息，无行动项 | 通知存档 |

**FR-4.3 提醒策略**（默认，可调）：

| 级别 | 提前量 | 次数 | 语气 |
|---|---|---|---|
| 5 | 24h / 2h / 30min | 3 | 强 |
| 4 | 24h / 1h | 2 | 较强 |
| 3 | 2h | 1 | 温和 |
| 2 | 当天 | 1 | 轻 |
| 1 | 无 | 0 | 静默 |

**FR-4.4 提醒推送**：Spring 定时扫描到期提醒 → 经发送桥 `send_message` 发到 QQ。每条提醒按「备忘 id + 提醒 id」独立幂等，重试不重复发送。
**FR-4.5 双闭环**：用户可在 QQ 内回「完成 / 取消」，也可在 Vue 上操作；两者都更新 `memo.status`。
**FR-4.6 状态机**：`ACTIVE → REMINDED → AWAITING_REPLY → DONE | CANCELLED`，另含 `OVERDUE`。
**FR-4.7 分类**：`学业 / 社交 / 健康 / 财务 / 日常 / 其他`，允许扩展自由标签。
**FR-4.8 置信度路由**：时间或要素不全的低置信备忘走 `type=MEMO` 草稿，确认后入库。

### FR-5 文件任务（复杂任务处理）

**FR-5.1 支持格式**：xlsx、docx 可读可写；pdf 只读（抽取文本用于理解，不回写）。
**FR-5.2 下载**：插件通过 NapCat HTTP 接口取文件；失败时换新 URL 重试，总尝试不超过 3 次；错误日志只保留 host 与状态码，**不得打印完整签名 URL**。
**FR-5.3 结构化**：插件把文件解析成「工作表/表格名 + 表头 + 已有行 + 单元格引用」的紧凑结构再送 Dify；**不得**把整表单元格全量塞给模型。
**FR-5.4 决策**：Dify 返回 `fills`（写什么到哪）、`missing`（缺哪些信息）、`confidence`、`needs_confirm`。插件只做机械写回，**不得**自行推断业务语义。
**FR-5.5 三种进入方式**（以下三种都必须正确，且插件内不得出现「空要求就自己反问」之类的语义分支）：

1. **先说要求再发文件**：文本先到 → `WAIT_FILE`；文件到达后按已述要求直接填，不再问。
2. **先发文件再补要求**：文件到达 → `ASK`（问要填什么）；后续文本作为补充继续该任务。
3. **同一条消息文本+文件**：直接填。

**FR-5.6 待填要求备份**：`WAIT_FILE` 时插件必须把要求按会话镜像到本地（含 TTL，默认 900s）；Dify 会话变量丢失时通过 `pending_request_hint` 恢复。
**FR-5.7 回传路由**：`confidence ≥ 阈值`（默认 0.85）且 `needs_confirm=false` → 直接回传 QQ；否则建 `type=FILE` 草稿，确认后发送。
**FR-5.8 状态镜像**：插件变更任务状态时同步到 Spring 的 `file_task`（只写读镜像，状态机真身仍在插件内），Vue 可读。
**FR-5.9 文件产物路径**：插件写出的文件必须落在 `send_bridge` 也能读到的同一路径下（容器同路径挂载），否则「文件不存在」。

**降级**：解析失败、写入失败、缺必填字段 → 明确告知用户，任务置 `FAILED` 或保持 `NEED_INPUT`，不得静默丢弃。

### FR-6 记忆（事实 / 风格分离）

**FR-6.1 事实记忆（实时写）**：Dify 从消息抽取事实（学号、姓名、专业、目标…）并判断**主语归属**：

- 明确「我本人」且 `confidence ≥ fact_auto_threshold`（默认 0.85）→ 直接 upsert；
- 置信度不足或主语不明（如「我室友学号是…」）→ 建 `type=FACT` 草稿。

**FR-6.2 事实冲突**：用户改口时**直接覆盖**旧值。
**FR-6.3 风格记忆（定期总结）**：定时任务按可配频率（每日+近 7 天 / 每日当日 / 每周）读取 `message_log`，调 Dify 风格总结工作流，写回 `style_profile`。**任何单条消息都不得触发画像更新。**
**FR-6.4 注入**：每次调 Dify 前由插件读取该用户事实与画像，作为输入变量注入。
**FR-6.5 记忆总控台（Vue）**：事实列表可增删改；风格画像可查看与手动编辑；总结频率可配。这是对「模型抽错」的最终兜底。

**验收**：用户在总控台删除某条事实后，下一次对话中助手不再使用它。

### FR-7 会话连续性

**FR-7.1 会话映射**：每个 `(botUuid, chatType, chatId, senderId)` 对应一个 Dify `conversation_id`，持久化在 `conversation_session`；插件先查内存缓存，再查 Spring，最后本地 JSON 兜底。
**FR-7.2 调用约定**：调 `/chat-messages` 必须带 `conversation_id`；首次会话由 Dify 返回后立即 `bind`。
**FR-7.3 失效恢复**：Dify 返回 `Conversation Not Exists` 时，清空映射并以新会话重试一次。
**FR-7.4 会话隔离**：私聊 `user = private:{sender_id}`；群聊 `user = group:{chat_id}:{sender_id}`，即**每个群成员独立会话**，不同人的待办文件任务不得互相污染。
**FR-7.5 重置**：用户说「重新开始」或调用 `conversations/reset` 时标记失效；插件缓存需在容器/进程重启后清空（已知行为，写进运维手册）。
**FR-7.6 保底**：Dify 侧会话变量可能因换应用或重置而丢失，因此待填要求等关键状态必须同时有 Spring / 插件的备份（FR-5.6）。

### FR-8 统一草稿中心

**FR-8.1 四类草稿**：`REPLY`（回复正文）/ `FILE`（文件引用与目标）/ `MEMO`（备忘字段）/ `FACT`（事实 kv），共用 `draft` 表。
**FR-8.2 状态**：`PENDING / CONFIRMED / REJECTED`；`PENDING` **不自动过期**，避免丢信息。
**FR-8.3 确认分发**：`POST /api/drafts/{id}/confirm` 按类型分发——`REPLY`/`FILE` 通知发送桥发 QQ；`MEMO`/`FACT` 写入对应业务表。
**FR-8.4 幂等**：重复确认同一草稿不得重复发送；`FILE` 发送成功后 `file_task.status → SENT`，失败保留或回滚为 `PENDING`。
**FR-8.5 群聊目标**：草稿 payload 必须携带 `targetType` / `targetId`，群聊草稿按群发送，**不得默认按私聊发**。

### FR-9 统一消息日志

**FR-9.1 写入**：插件在每条消息进出时异步写 `message_log`（`direction IN/OUT`），含 `conversation_id`、`message_id`、`dedupe_key`、`task_ref`。
**FR-9.2 去重**：`dedupe_key` 唯一，重复投递不重复记账。
**FR-9.3 查询**：`GET /api/message-logs` 支持按会话/方向查询，供风格总结与全链路排查。
**FR-9.4 一致性**：发给用户的每一条可见输出（回复、追问、提醒、文件）都必须有 OUT 记录。

### FR-10 配置与运维

**FR-10.1 插件配置项**：Spring 地址与超时、Dify 地址/Key/超时/文件工作流 Key、NapCat 地址与 Token、机器人 UUID 与 QQ、群触发前缀、事实自动写入阈值、文件确认阈值、拟人延迟四参数、拦截刷新周期与作用域。
**FR-10.2 敏感信息**：API Key / Token / 数据库口令一律走配置或 `.env`，**不得**硬编码进代码或提交进仓库。
**FR-10.3 部署**：LangBot（含插件运行时）+ NapCat + 发送桥以 Docker Compose 部署在 Linux 虚拟机；Spring Boot 与 Dify 可独立部署。

## 6. 接口需求

完整请求/响应见 [`api_contract.md`](./api_contract.md)。需求层面只约束分组成员与调用方。

### 6.1 Spring Boot 对外 API（10 组 31 个端点）

| 分组 | 端点 | 调用方 |
|---|---|---|
| 草稿 | `POST/GET /api/drafts`、`POST /api/drafts/{id}/confirm`、`POST /api/drafts/{id}/reject` | 插件 / Dify / Vue |
| 消息日志 | `POST /api/message-logs`、`GET /api/message-logs` | 插件 / 发送桥 / Vue |
| 备忘录 | `POST /api/memos`、`GET /api/memos`、`PATCH /api/memos/{id}` | Dify / Vue / 插件 |
| 防重与拦截 | `POST /api/collection-tasks/check`、`/mark`、`GET /api/collection-tasks/rules`、`/api/intercept-rules` CRUD | 插件 / Vue |
| 画像与设置 | `/api/profile/{senderId}`、`/api/profile/facts` CRUD、`/api/style-profile/{senderId}`、`/api/style-profile/update`、`GET/PUT /api/settings` | 插件 / Dify / Vue |
| 文件任务 | `GET /api/file-tasks`、`POST /api/file-tasks/sync` | Vue / 插件 |
| 会话映射 | `/api/conversations/resolve`、`/bind`、`/reset` | 插件 |

**统一约定**：响应体 `{code, message, data}`；成功 `code=0`；参数错误 `400`；系统错误 `500`；时间用 ISO-8601 本地时间；个人内网项目暂不做鉴权与分页。

### 6.2 主动发送接口（发送桥）

| 端点 | 用途 | 关键要求 |
|---|---|---|
| `POST /api/langbot/send_message` | 发文本 | 私聊拟人延迟；`bizRef` 幂等 |
| `POST /api/langbot/send_file` | 发文件 | 与发文本**分开的契约**，绝不混用；文件通道在 LangBot 4xx 时回落 NapCat |
| `GET /health` | 健康检查 | 返回 `code=0` |

**幂等**：同一 `bizRef` 在途时返回 409，重试返回首次的 `messageId`；状态落盘持久化，重启不丢。

### 6.3 Dify ↔ 插件

Dify Chatflow 的 Start 节点共 **14 个变量**，且必须与插件发送的键一一对应（少一个 Dify 直接 400）。其中 13 个由插件的 `inputs` 填充——`event_type`、`facts`、`style_prompt`、`chat_type`、`chat_id`、`sender_id`、`current_time`、`file_task_ref`、`file_name`、`file_kind`、`structure`、`pending_request_hint`、`last_task_ref`——**全部序列化为字符串**；第 14 个 `query` 走 `/chat-messages` 的顶层 `query` 字段。返回 Answer 必须是纯 JSON 决策 envelope，动作集合为：

`SEND / DRAFT / SILENT / MEMO / FACT / MEMO_CLOSE / WAIT_FILE / ASK / FILE_FILL`

未知动作、缺必填字段：降级为 `SILENT` 并记日志。

## 9. 验收标准

### 9.1 功能验收（真机，按 UC 顺序）

1. **UC-01**：私聊「你好」→ 收到像本人的回复；`_debug.log` 出现 `dify ok ... action=SEND`。
2. **UC-02**：群里发收集通知 → 回复一次；第二人再发同样通知 → 不重复回复。
3. **UC-04**：发「我要发个文件，把姓名填上」→ 回「发过来吧」→ 发 xlsx → **不再反问**，按已述要求填。
4. **UC-05**：先发 xlsx → 机器人问要填什么 → 回「姓名张三」→ 按补充信息填。
5. **UC-06**：构造低置信填写 → 生成 FILE 草稿 → Vue 确认 → QQ 真的收到文件 → `file_task.status = SENT`。
6. **UC-03/07**：说一件带时间的事 → 备忘入库 → 到点收到提醒 → 回「做完了」→ 状态变 DONE。
7. **UC-08**：总控台删掉一条事实 → 下一轮对话不再使用该事实。
8. **群聊 @ 规则**：群里不 @ 的普通消息，机器人不响应。

### 9.2 工程验收

- Python 插件与发送桥测试全绿；Java `mvn test` 全绿。
- `docker compose config` 通过；4 个服务 `running`。
- 仓库内无明文的第三方 API Key（数据库口令作为本地开发配置的已知例外，须在 README 标注）。

### 9.3 禁止性验收（出现即不通过）

- 用户收到未解析的 JSON 原文或 Python 异常栈。
- 重复确认草稿导致重复发送。
- 群聊未 @ 时机器人主动发言（提醒推送除外，且提醒须发私聊）。
- 同一收集任务重复回复。

## 附录 B · 术语

| 术语 | 含义 |
|---|---|
| 决策 envelope | Dify Answer 节点输出的纯 JSON，含 `action` 与各动作 payload |
| 降级 | 异常或低置信时退回更安全的行为（草稿 / 静默 / 追问），而不是报错或乱发 |
| 前置拦截 | 插件在调用 Dify 之前用关键词 + 正则直接命中固定回复 |
| `task_key` | 防重键：`chat_id + task_type + 时间窗口` |
| `task_ref` | 插件侧文件任务 id，用于跨轮引用同一份文件 |
| 拟人延迟 | 私聊发送前按字数模拟的等待时间（含随机抖动） |
| 置信度路由 | 依 `confidence` 决定「直接执行」还是「转草稿」 |
| 状态镜像 | `file_task` 表：Spring 侧只读副本，状态机真身在插件 |
| `bizRef` | 主动发送的幂等键，同一键只成功发送一次 |
